### `open` 函数详解

#### 1. 函数原型

```c
/* 不定量参数 */
int open(const char *pathname, int flags, .../*mode_t mode*/);
```

---

#### 2. 参数说明

- **`pathname`**：要打开或创建的文件路径。
- **`flags`**：文件的打开方式（必填），可通过按位或运算符 `|` 组合多个标志。

可选参数，只有在 `flags` 包含 **O_CREAT** 才会使用这个参数

- **`mode`**：文件的访问权限（可选），仅在 `flags` 中包含 `O_CREAT` 时会使用。

---

#### 3.返回值

- **成功时**：返回一个**非负整数**，即**文件描述符**（File Descriptor）。
- **失败时**：返回 **`-1`**，并设置全局变量 `errno` 以指示具体错误类型。

---

#### 4. 所需头文件（按需包含）

| 头文件                   | 必要性                    | 说明                                                         |
| ------------------------ | ------------------------- | ------------------------------------------------------------ |
| `#include <fcntl.h>`     | **必须**                  | 包含 `open` 函数声明，以及所有 `O_*` 标志位（如 `O_RDONLY`、`O_CREAT`、`O_APPEND` 等）。若缺失，编译器会报“未定义标识符”错误，且隐式声明可能引发运行时问题。 |
| `#include <sys/types.h>` | **强烈建议**              | 定义 `mode_t`、`off_t`、`size_t` 等 POSIX 标准数据类型。虽然部分系统在 `<fcntl.h>` 中间接包含，但显式引入可提升代码在不同 Unix/Linux 平台上的可移植性。 |
| `#include <sys/stat.h>`  | **使用 `O_CREAT` 时必须** | 定义 `S_IRUSR`、`S_IWUSR`、`S_IXGRP` 等文件权限宏，用于构造 `mode` 参数。当然，你也可以直接用八进制数（如 `0644`），但使用宏更易读、更专业。 |

---

#### 5. `flags` 参数：打开方式

| 标志         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| **O_RDONLY** | 只读打开                                                     |
| **O_WRONLY** | 只写打开                                                     |
| **O_RDWR**   | 读写打开                                                     |
| **O_CREAT**  | 文件不存在则创建，此时需提供 `mode` 参数以设置新文件的访问权限 |
| **O_APPEND** | 追加写入，数据写入文件末尾，不覆盖原有内容                   |

**注意**：

- **前三个标志（O_RDONLY / O_WRONLY / O_RDWR）是必选项，且三者必须且只能选择其中一个。**
- **O_CREAT** 和 **O_APPEND** 是可选项，用于对前三个基本模式进行补充修饰，可用 `|` 组合。

---

#### 6. `mode` 参数：文件权限（仅在 `O_CREAT` 时使用）

`mode` 用于设定新建文件的访问权限，常用宏如下（可用 `|` 组合）：

| 宏                          | 含义           | 适用对象            |
| --------------------------- | -------------- | ------------------- |
| S_IRUSR / S_IWUSR / S_IXUSR | 读 / 写 / 执行 | 文件所有者（User）  |
| S_IRGRP / S_IWGRP / S_IXGRP | 读 / 写 / 执行 | 文件所属组（Group） |
| S_IROTH / S_IWOTH / S_IXOTH | 读 / 写 / 执行 | 其他用户（Other）   |

---

#### 7. 补充：创建文件的专用函数

虽然使用 `open` 并带上 `O_CREAT` 可以创建文件，但 Linux 也提供了更简洁的接口：

```c
int creat(const char *pathname, mode_t mode);
```

该函数专门用于创建文件，等价于：

```c
open(pathname, O_WRONLY | O_CREAT | O_TRUNC, mode);
```

### 二、`read` 函数详解

#### 1. 函数原型
```c
ssize_t read(int fd, void *buf, size_t count);
```

#### 2. 参数说明
- **`fd`**：文件描述符，指向已打开的文件、网络套接字、串口或其他设备。
- **`buf`**：指向内存缓冲区的指针，用于存放读取到的数据。
- **`count`**：请求读取的字节数（`size_t` 类型，无符号）。

#### 3. 返回值（`ssize_t` 类型）
- **成功**：返回实际读取的字节数（非负，可能小于 `count`，如读到文件末尾）。
- **失败**：返回 `-1`，并设置全局 `errno` 以指示具体错误。
- **返回 0**：表示已到达文件末尾（EOF），没有更多数据可读。

---

#### 4. 所需头文件
| 头文件                   | 必要性       | 说明                                                         |
| ------------------------ | ------------ | ------------------------------------------------------------ |
| `#include <unistd.h>`    | **必须**     | 提供 `read`、`write`、`close` 等系统调用函数声明。           |
| `#include <sys/types.h>` | **强烈建议** | 提供 `ssize_t`、`size_t` 等 POSIX 标准类型定义，保证代码可移植性。 |

---

#### 5. 使用示例
```c
char buffer[4096] = "";

// 从 fd 读取数据到 buffer 的起始位置
read(fd, buffer, sizeof(buffer));

// 从 fd 读取数据到 buffer 的偏移 256 字节处
read(fd, buffer + 256, sizeof(buffer) - 256);
```

**特点**：
- 可以从多个不同文件读取数据，汇聚到同一个缓冲区（如示例中的 `buffer`）。
- 支持从任意偏移位置写入缓冲区，方便组装数据包或解析文件格式。

---

#### 6. 典型应用场景
- **文件读取**：从普通文件中读取内容。
- **网络数据接收**：从网络套接字读取数据包。
- **设备通信**：从串口、管道等设备读取数据。
- **格式解析**：读取数据到结构体指针，用于解析 ELF 文件、网络协议包等二进制格式（需注意内存对齐和字节序）。

---

#### 7. 类型详解：`size_t` 与 `ssize_t`

| 类型          | 符号   | 用途                                                         |
| ------------- | ------ | ------------------------------------------------------------ |
| **`size_t`**  | 无符号 | 表示对象大小或长度。如 `sizeof` 的返回值、`strlen` 的返回值、`malloc` 的参数、`read`/`write` 的 `count` 参数。 |
| **`ssize_t`** | 有符号 | 表示“要么成功返回大小，要么失败返回错误码”。`read`/`write` 返回此类型，成功时返回字节数（非负），失败时返回 `-1` 并设置 `errno`。 |

---

### `write` 函数详解

#### 1. 函数原型
```c
ssize_t write(int fd, const void *buf, size_t count);
```

#### 2. 参数说明
- **`fd`**：文件描述符，可以是文件、网络套接字、串口、管道或其他设备。
- **`buf`**：指向内存缓冲区的指针，包含要写入的数据。
- **`count`**：请求写入的字节数。

#### 3. 返回值（`ssize_t` 类型）
- **成功**：返回实际写入的字节数（非负，可能小于 `count`，如磁盘空间不足）。
- **失败**：返回 `-1`，并设置全局 `errno`。

---

#### 4. 所需头文件

| 头文件                   | 必要性       | 说明                                                         |
| ------------------------ | ------------ | ------------------------------------------------------------ |
| `#include <unistd.h>`    | **必须**     | 提供 `read`、`write`、`close` 等系统调用函数声明。           |
| `#include <sys/types.h>` | **强烈建议** | 提供 `ssize_t`、`size_t` 等 POSIX 标准类型定义，保证代码可移植性。 |

#### 5. 使用示例
```c
char buffer[4096] = "Hello, World!";

// 将 buffer 全部内容写入 fd
write(fd, buffer, strlen(buffer));

// 将 buffer 中从偏移 256 开始的 100 字节写入 fd
write(fd, buffer + 256, 100);
```

**特点**：
- 可以从同一个内存段的不同偏移位置，分别写入到不同文件。
- 目标 `fd` 可以是文件、网络连接、串口等，统一接口便于编程。

### `close` 函数详解

#### 1. 函数原型
```c
int close(int fd);
```

#### 2. 功能说明
关闭一个已打开的文件描述符，释放其占用的系统资源。

#### 3. 返回值
- **成功**：返回 `0`。
- **失败**：返回 `-1`，并设置 `errno`。

#### 4. 所需头文件
| 头文件                | 必要性   | 说明                                               |
| --------------------- | -------- | -------------------------------------------------- |
| `#include <unistd.h>` | **必须** | 提供 `read`、`write`、`close` 等系统调用函数声明。 |

#### 5. 重要注意事项
- **及时关闭**：文件描述符是有限资源。每个进程可同时打开的文件数量是有限的（通常为 **4096**，可通过 `ulimit -n` 查看）。
- **资源泄漏**：若未及时关闭，可能耗尽系统资源，导致后续 `open` 或 `socket` 调用失败。
- **自动关闭**：进程终止时，系统会自动关闭所有打开的文件描述符，但依赖此机制是不良习惯。

### 三、`dup` 和 `dup2` 函数详解

#### 1. 函数原型
```c
int dup(int oldfd);
int dup2(int oldfd, int newfd);
```

---

#### 2. 功能说明
- **`dup(oldfd)`**：复制文件描述符 `oldfd`，返回一个新的文件描述符，两者指向内核中**同一个文件对象**。
- **`dup2(oldfd, newfd)`**：将 `newfd` 也指向 `oldfd` 所指向的文件对象。若 `newfd` 已打开，则先关闭它。

**核心本质**：两个不同的文件描述符指向同一个内核文件对象（`struct file`），共享文件偏移量、文件状态标志等属性。

---

#### 3. 返回值
- **`dup`**：成功时返回新的文件描述符（系统自动分配的最小可用值）；失败返回 `-1`，并设置 `errno`。
- **`dup2`**：成功时返回 `newfd`；失败返回 `-1`，并设置 `errno`。

---

#### 4. 所需头文件
| 头文件                | 必要性   | 说明                                                         |
| --------------------- | -------- | ------------------------------------------------------------ |
| `#include <unistd.h>` | **必须** | 提供 `dup`、`dup2` 函数声明，以及 `STDIN_FILENO`、`STDOUT_FILENO`、`STDERR_FILENO` 等标准文件描述符常量。 |

---

#### 5. 核心铺垫：Linux 文件模型的三层结构

在 Linux 内核中，一个被打开的文件并非只靠一个 `int` 数字维系，而是由三层数据结构共同描述：

1. **进程级：文件描述符表 (fd table)**
   - 位于进程控制块（`task_struct`）中。
   - 本质是一个指针数组，下标就是 `fd`（如 0, 1, 2）。
   - 每个指针指向内核中的**文件对象**。
   - **关键属性**：`close-on-exec` 标志（FD_CLOEXEC）。

2. **内核级：文件对象 (file object)**
   - 结构体 `struct file`。
   - 这是 `dup` 系列函数**真正操作的对象**。
   - 包含关键字段：
     - `f_path`：指向底层 dentry/inode（即具体文件）。
     - `f_pos`：**当前文件偏移量（读写位置）**。
     - `f_count`：**引用计数**（有多少个 fd 指向它）。
     - `f_flags`：打开标志（如 `O_RDWR`, `O_APPEND`, `O_NONBLOCK`）。

3. **设备级：索引节点 (inode) 与 dentry**
   - 代表磁盘或设备上的具体资源（硬盘文件、Socket、管道）。

---

#### 6. `dup()` 和 `dup2()` 的本质

当你调用它们时，内核做的事可以精确描述为：

- **`dup(oldfd)`**：
  1. 在进程的 fd 表中找到**最小的空闲下标**（newfd）。
  2. 将 `newfd` 的指针指向 `oldfd` 所指向的那个 `struct file`。
  3. 执行 `struct file` 的 `f_count++`（引用计数加 1）。
  4. **不会复制** `struct file` 本身，更不会复制 inode。

- **`dup2(oldfd, newfd)`**：
  1. 如果 `newfd` 已打开，先关闭它（关闭时 `f_count--`，若归零则销毁 file 对象）。
  2. 将 `newfd` 指向 `oldfd` 的 `struct file`。
  3. 引用计数加 1。

---

#### 7. 深层次的影响（与普通 `open` 的区别）

**这是最容易被忽视的点：**

1. **共享文件偏移量（`f_pos`）**：
   - 如果你用 `open` 两次打开同一个物理文件，你会得到**两个独立的 `struct file`**，它们有各自的 `f_pos`，所以读 A 不会影响 B 的读取位置。
   - 但如果你用 `dup` 复制出一个新 fd，这两个 fd **共享同一个 `f_pos`**。在 A 中 `read` 了 10 个字节，B 中再 `read` 会从第 11 个字节开始。

2. **共享文件状态标志（`f_flags`）**：
   - 通过 `fcntl(fd, F_SETFL, ...)` 修改 `O_NONBLOCK` 或 `O_APPEND`，会影响所有 dup 出来的 fd。

3. **引用计数决定资源释放时机**：
   - 一个文件对象只有在 `f_count` 变为 0 时才会真正关闭（释放内核资源）。
   - 因此，你 `close(oldfd)` 后，`newfd` 依然有效，因为 `f_count` 只是从 2 变成 1。

---

#### 8. 典型应用场景的深层原因

##### 场景一：标准输入输出重定向（Shell 实现）

```c
// 将 stdout 重定向到文件
int fd = open("log.txt", O_WRONLY | O_CREAT, 0644);
dup2(fd, STDOUT_FILENO);  // 使标准输出 fd 指向 log.txt 的 file 对象
close(fd);                // 只是减少引用计数，stdout 依然指向它
```

- 为什么用 `dup2` 而不是直接 `close(1); open(...)`？因为 `open` 不一定能保证分配到 `1` 号位，而 `dup2` 强制指定。

##### 场景二：进程间管道通信

```c
pipe(pipefd);   // pipefd[0] 读端，pipefd[1] 写端
dup2(pipefd[1], STDOUT_FILENO);
```

- 父子进程通过 `dup` 共享管道的 `struct file`，因此父进程写、子进程读时，它们操作的是**同一个内核缓冲区**，且共享 `f_pos`（虽然管道不关心偏移量，但共享的缓冲区状态是关键）。

---

#### 9. `dup` 与 `dup2` 的关键差异

| 维度         | `dup`              | `dup2`                                                       |
| :----------- | :----------------- | :----------------------------------------------------------- |
| **目标 fd**  | 自动选取最小可用值 | 由你指定                                                     |
| **原子性**   | 是原子的           | **`dup2` 是原子的**（关闭 newfd 并重指向合为一步）           |
| **竞争风险** | 无竞争风险         | 在多线程环境下，`dup2` 确保了不会出现“关闭后、重指向前”被其他线程插入 `open` 的情况 |
| **返回值**   | 返回新 fd          | 返回 newfd                                                   |

**经典坑点**：如果你用 `close(newfd); dup(oldfd);` 来模拟 `dup2`，在多线程下极其危险，因为两步之间可能被信号中断或被其他线程抢占。

---

#### 10. 现代扩展：`dup3()`（Linux 专有）

```c
int dup3(int oldfd, int newfd, int flags);
```

`dup3` 比 `dup2` 多了一个特性：

- 支持 `O_CLOEXEC` 标志。
- 意义：让新 fd 在执行 `exec` 族函数时自动关闭，防止子进程意外继承不该继承的 fd（提升安全性，避免 fd 泄漏）。

---

#### 11. 总结一句哲学本质

> **`open` 创建文件对象，而 `dup` 只是增加对同一对象的引用。**  
> 它不是“复制文件”，而是“复制指向文件的指针”。  
> 这种设计让 Linux 实现了**描述符的轻量化共享**，支撑起了管道、重定向、进程替换等所有 UNIX 哲学的基石。

### `fsync` 函数详解

#### 1. 函数原型
```c
int fsync(int fd);
```

#### 2. 功能说明
将文件描述符 `fd` 所关联文件的**所有已修改数据**和**元数据**（如文件大小、修改时间等）从内存缓冲区（页缓存）**强制写入磁盘**，确保数据持久化存储。

简单说：**调用 `fsync` 后，数据才真正“落盘”**，即使系统突然断电或崩溃，数据也不会丢失。

---

#### 3. 返回值
- **成功**：返回 `0`，所有数据已成功写入磁盘。
- **失败**：返回 `-1`，并设置全局 `errno` 以指示具体错误（如 `EIO` 表示磁盘 I/O 错误）。

---

#### 4. 所需头文件

| 头文件                | 必要性   | 说明                                                         |
| --------------------- | -------- | ------------------------------------------------------------ |
| `#include <unistd.h>` | **必须** | 提供 `fsync`、`fdatasync`、`sync` 等数据同步系统调用的函数声明。此外，`close`、`read`、`write`、`dup` 等文件操作函数也在此头文件中声明。POSIX 标准明确规定此头文件为这些函数声明的所在地，缺少它将导致编译期隐式声明警告或错误。 |

---

#### 5. 为什么需要 `fsync`？

现代操作系统为了提升 I/O 性能，并不会在每次 `write` 调用时立即将数据写入磁盘，而是：
1. 先将数据暂存在**内核页缓存（Page Cache）**中。
2. 由内核后台线程（如 `flush`/`pdflush`）择机写入磁盘。
3. 若在数据落盘前系统崩溃或断电，缓存中的未写入数据将**永久丢失**。

因此，对于关键数据（如数据库事务日志、配置文件修改、计费记录等），必须调用 `fsync` 确保数据已安全落盘。

### 四、`lseek` 函数详解

#### 1. 函数原型
```c
off_t lseek(int fd, off_t offset, int whence);
```

---

#### 2. 功能说明
移动文件描述符 `fd` 所关联文件的**读写位置**（即文件偏移量，`f_pos`）。`lseek` 仅修改内核中文件对象的偏移量，**不触发任何实际的 I/O 操作**。

---

#### 3. 返回值
- **成功**：返回从文件开头到新位置的偏移量（字节数），类型为 `off_t`。
- **失败**：返回 `(off_t)-1`，并设置全局 `errno`（如 `EBADF` 表示无效文件描述符，`EINVAL` 表示 `whence` 无效或偏移量超出文件大小限制等）。

---

#### 4. 所需头文件
| 头文件                   | 必要性       | 说明                                                         |
| ------------------------ | ------------ | ------------------------------------------------------------ |
| `#include <unistd.h>`    | **必须**     | 提供 `lseek` 函数声明，以及 `SEEK_SET`、`SEEK_CUR`、`SEEK_END` 这三个常量宏定义。 |
| `#include <sys/types.h>` | **强烈建议** | 提供 `off_t` 类型定义。POSIX 标准明确要求在使用 `lseek` 时包含此头文件以确保 `off_t` 类型可见，提升代码跨平台可移植性。虽然在许多 Linux 发行版中 `<unistd.h>` 已间接包含它，但显式包含是良好习惯。 |

---

#### 5. `whence` 参数详解

| 常量         | 起点位置             | offset 正负 | 说明                                                         |
| ------------ | -------------------- | ----------- | ------------------------------------------------------------ |
| **SEEK_SET** | 文件开头             | 必须 ≥ 0    | 将读写位置设置为 `offset` 字节处。不支持负数。               |
| **SEEK_CUR** | 当前文件指针所在位置 | 可为正或负  | 在当前位置基础上增加 `offset` 个位移量。允许负值（向前移动）。 |
| **SEEK_END** | 文件末尾（EOF）      | 可为正或负  | 在文件末尾基础上增加 `offset` 个位移量。允许负值（向后移动），但移动后位置必须 ≥ 0。 |

---

#### 6. 函数名历史由来（`l` 前缀的含义）

`lseek` 的名字来源于早期 Unix 系统：

- **`seek`**：表示“移动文件读写指针”这个操作本身。
- 前缀 **`l`**：表示该函数的**返回值类型是 `long`**（长整型）。

在更古老的 Unix 版本中，还有一个 **`seek`** 函数（注意没有 `l`），它的 `offset` 和返回值都是 `int` 类型（16 位），最大只能表示 32767 字节，这在当时对于小文件够用。但随着文件越来越大，16 位 `int` 不够用了，于是引入了 **`lseek`**（`long seek`），使用 32 位的 `long` 类型，可以支持更大的文件（最大 2GB）。

现代系统中：
- `off_t` 通常被定义为 `long` 或 `long long`（取决于系统是否支持大文件，如 `_FILE_OFFSET_BITS=64` 时可支持超过 2GB 的大文件）。
- 虽然参数类型已演变为 `off_t`，但函数名 `lseek` 作为历史遗留名称被保留了下来。

---

#### 7. 使用示例

```c
#include <unistd.h>
#include <sys/types.h>
#include <fcntl.h>

int fd = open("file.txt", O_RDWR);
if (fd < 0) {
    perror("open");
    return 1;
}

// 移动到文件开头偏移 100 字节处
lseek(fd, 100, SEEK_SET);

// 从当前位置向后移动 50 字节（即前进到 150 字节处）
lseek(fd, 50, SEEK_CUR);

// 移动到文件末尾（用于确定文件大小）
off_t file_size = lseek(fd, 0, SEEK_END);

// 移动到文件末尾前 10 字节处
lseek(fd, -10, SEEK_END);

close(fd);
```

---

#### 8. 典型应用场景

1. **随机读写**：在文件中跳转到任意位置进行读取或写入，适用于数据库文件、索引文件等。
2. **获取文件大小**：`lseek(fd, 0, SEEK_END)` 返回文件总字节数（比 `stat` 系统调用更轻量）。
3. **文件空洞（Hole）创建**：使用 `lseek` 越过一段空间后再写入，可在稀疏文件中创建空洞，节省磁盘空间。
4. **重新读取已读数据**：将位置移回之前的位置，实现“重放”读取。

---

#### 9. 注意事项

1. **不影响 I/O 操作**：`lseek` 只是修改内核中 `struct file` 的 `f_pos` 字段，并不实际移动磁盘磁头或读取任何数据。
2. **对管道、FIFO、Socket 无效**：`lseek` 对管道、FIFO、Socket 等特殊文件无效，调用会返回 `-1` 并设置 `errno` 为 `ESPIPE`（非法定位）。
3. **支持超出文件末尾的偏移**：可以将读写位置移动到文件当前末尾之后（即文件空洞），再写入数据时会以零字节填充空洞区域（取决于文件系统支持）。
4. **与 `O_APPEND` 的互斥**：若文件以 `O_APPEND` 方式打开，每次 `write` 都会强制从文件末尾写入，无论 `lseek` 如何设置位置。

### `mkstemp` 函数详解

#### 1. 函数原型
```c
int mkstemp(char *template);
```

---

#### 2. 功能说明
生成一个**唯一的临时文件名**，并**原子地创建并打开**该文件，返回文件描述符。该文件以读写模式打开，权限为 `0600`（仅所有者可读写），且文件是临时的，不保证数据长期有效。

---

#### 3. 返回值
- **成功**：返回文件描述符（非负整数），可用于 `read`、`write`、`close` 等操作。
- **失败**：返回 `-1`，并设置全局 `errno` 以指示具体错误。

---

#### 4. 所需头文件

| 头文件                | 必要性   | 说明                                                         |
| --------------------- | -------- | ------------------------------------------------------------ |
| `#include <stdlib.h>` | **必须** | 提供 `mkstemp` 函数声明。此头文件是 C 标准库的一部分，包含内存分配、进程控制、字符串转换等实用函数。`mkstemp` 的 POSIX 标准声明即位于此头文件中。 |

---

#### 5. `template` 参数格式
- **格式**：前缀 + `XXXXXX`（六个大写的 X）
- 前缀可以为任意字符串（含路径），但**后缀必须恰好是六个 `X`**
- 函数会**替换**这六个 `X` 为随机字符，以生成唯一文件名

**示例**：
```c
char template[] = "/tmp/myapp_temp_XXXXXX";
mkstemp(template);
// 执行后，template 可能变为 "/tmp/myapp_temp_AbC3Xy"
```

---

#### 6. 历史渊源：`mktemp()` 与安全问题

在 `mkstemp()` 出现之前，创建一个临时文件的“标准”做法是使用 **`mktemp()`** 函数（注意没有 `s`）：

```c
char *mktemp(char *template);
```

- `mktemp()` **只生成一个不存在的文件名**，但**不会实际创建文件**
- 这会导致一个严重的安全问题：**竞态条件（TOCTOU）**

---

#### 7. 竞态条件问题（TOCTOU）

典型的错误用法：

```c
char name[] = "/tmp/fileXXXXXX";
mktemp(name);          // 生成一个不存在的文件名
int fd = open(name, O_CREAT | O_RDWR, 0600);  // 再创建文件
```

**问题**：在 `mktemp()` 和 `open()` 之间，攻击者可以：
1. 预测你将要创建的文件名
2. 抢先创建一个同名文件（可能是指向敏感文件的符号链接）
3. 当你 `open()` 时，可能覆盖或破坏攻击者指定的文件

这就是典型的 **TOCTOU（Time Of Check To Time Of Use）** 漏洞。

---

#### 8. `mkstemp()` 的安全性

```c
int mkstemp(char *template);
```

- `mkstemp()` 中的 **`s` = `secure`**
- 它**原子地**完成两件事：
  1. 生成一个唯一的文件名
  2. **立即创建并打开该文件**（返回文件描述符）
- 两步操作之间没有时间窗口，从根本上杜绝了竞态条件

此外，`mkstemp()` 还会：
- 以 **读写模式** 打开文件
- 设置权限为 **0600**（仅所有者可读写）
- 确保文件**不会被其他进程劫持**

---

#### 9. 相关函数对比

| 函数      | 含义                                   | 安全性                                              |
| --------- | -------------------------------------- | --------------------------------------------------- |
| `mktemp`  | `make temp`（生成临时文件名）          | **不安全**，仅生成名字不创建文件，存在 TOCTOU 漏洞  |
| `mkstemp` | `make secure temp`（安全创建临时文件） | **安全**，原子创建+打开，返回 fd                    |
| `tmpfile` | 标准库函数，自动创建临时文件（流式）   | **安全**，返回 `FILE*` 流，程序关闭或结束时自动删除 |

---

#### 10. 使用示例

```c
#include <stdlib.h>
#include <unistd.h>
#include <stdio.h>

int main() {
    char template[] = "/tmp/myapp_XXXXXX";
    
    int fd = mkstemp(template);
    if (fd < 0) {
        perror("mkstemp");
        return 1;
    }
    
    printf("临时文件已创建：%s\n", template);
    
    // 使用临时文件...
    write(fd, "temp data", 9);
    
    // 关闭并删除临时文件（可选）
    close(fd);
    unlink(template);  // 删除文件
    // 即使 unlink 后，只要 fd 还开着，进程仍可继续读写
    
    return 0;
}
```

---

#### 11. 总结

**`s` = `secure`**，表示这个函数是 `mktemp()` 的安全增强版本，通过**原子创建+打开**来避免 TOCTOU 竞态条件漏洞。

> **现代编程中，应该始终使用 `mkstemp()` 而不是 `mktemp()`**——实际上，`mktemp()` 在 Linux 手册中已经被标记为 **DEPRECATED（废弃）** 了。

### 五、`flock` 函数详解

#### 1. 函数原型
```c
int flock(int fd, int operation);
```

---

#### 2. 功能说明
对文件施加**建议性锁**（advisory lock），用于协调多个进程对同一文件的并发访问。所谓“建议性”，意味着内核不会强制阻止对文件的读写，但协作的进程会通过检查锁来避免冲突。若某个进程不调用 `flock` 而直接 `read/write`，依然可以操作文件。

---

#### 3. 返回值
- **成功**：返回 `0`。
- **失败**：返回 `-1`，并设置全局 `errno` 以指示具体错误（如 `EWOULDBLOCK` 表示非阻塞模式下无法获取锁，`EBADF` 表示无效文件描述符等）。

---

#### 4. 所需头文件

| 头文件                  | 必要性       | 说明                                                         |
| ----------------------- | ------------ | ------------------------------------------------------------ |
| `#include <sys/file.h>` | **必须**     | 提供 `flock` 函数声明，以及 `LOCK_SH`、`LOCK_EX`、`LOCK_UN`、`LOCK_NB` 等所有锁操作宏定义。此头文件是 BSD 风格的锁操作接口所在地。 |
| `#include <unistd.h>`   | **隐含必需** | 虽然 `flock` 的声明在 `<sys/file.h>` 中，但实际使用时通常需要 `open`、`close`、`read`、`write` 等文件操作函数，这些函数声明于 `<unistd.h>`。此外 `flock` 内部依赖 `errno`，通常与 `<errno.h>` 配合使用。 |

---

#### 5. `operation` 参数详解

`operation` 参数通过按位或（`|`）组合以下常量：

##### 基础操作（必须选其一）

| 常量          | 含义           | 行为                                   | 冲突规则                                                     |
| ------------- | -------------- | -------------------------------------- | ------------------------------------------------------------ |
| **`LOCK_SH`** | 共享锁（读锁） | 多个进程可**同时**持有同一文件的共享锁 | 持有 `LOCK_SH` 时，其他进程可继续加 `LOCK_SH`，但**无法**加 `LOCK_EX`，会被阻塞 |
| **`LOCK_EX`** | 独占锁（写锁） | 同一时间**只能有一个**进程持有         | 持有 `LOCK_EX` 时，其他进程无论加 `LOCK_SH` 还是 `LOCK_EX`，都会被阻塞 |
| **`LOCK_UN`** | 解锁           | 释放当前进程持有的文件锁               | —                                                            |

> **注意**：文件被关闭（`close`）时，内核会自动释放该进程持有的所有文件锁。但 `LOCK_UN` 是显式解锁，两者之间可能存在微小的时间差，建议显式解锁以确保确定性行为。

##### 组合选项（修改阻塞行为）

| 常量          | 含义                   | 行为                                                         |
| ------------- | ---------------------- | ------------------------------------------------------------ |
| **`LOCK_NB`** | 非阻塞（Non-blocking） | 与 `LOCK_SH` 或 `LOCK_EX` 做 `\|` 组合（如 `LOCK_EX \| LOCK_NB`）。若无法立即获得锁，**不会等待**，而是立即返回 `-1`，`errno` 设为 `EWOULDBLOCK` |

---

#### 6. 典型应用场景

1. **添加 `LOCK_SH` 只读锁**：防止文件在读取过程中被篡改导致数据冲突。
2. **使用 `LOCK_EX` 防止程序多实例**：程序启动时对某个文件添加互斥锁，若加锁失败则说明已有实例在运行，直接退出。
3. **生产者消费者模型**：使用 `LOCK_EX` 实现多个程序竞争文件控制权，用于消息分发或文件处理等场景。
4. **进程间协作**：多个进程遵循同一锁协议，确保对共享文件的一致性访问。

---

#### 7. 特别提醒（常见陷阱）

- **锁与文件描述符（fd）绑定**：锁是与打开的文件表项（`struct file`）关联的，而非 fd 变量。如果你复制了 fd（通过 `dup` 或 `fork`），所有副本共享同一个锁。**关闭任何一个副本（`close`）都会释放该锁**，这与记录锁（`fcntl`）不同。

- **建议性而非强制性**：如果某个进程不调用 `flock`，直接调用 `read/write` 依然可以操作文件。`flock` 只能保护“守规矩”的进程。

- **`flock` 与 `fcntl` 锁不互通**：`flock` 和 `fcntl` 是两套独立的锁机制，互相感知不到对方的锁。同一进程在同一文件上混用二者可能导致意外行为。

---

#### 8. 使用示例

```c
#include <sys/file.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>
#include <errno.h>

int main() {
    int fd = open("test.txt", O_RDWR);
    if (fd < 0) {
        perror("open");
        return -1;
    }

    // 尝试加独占锁，若已被占则不等待
    if (flock(fd, LOCK_EX | LOCK_NB) == -1) {
        if (errno == EWOULDBLOCK) {
            printf("文件已被其他进程锁定，稍后重试\n");
        }
        close(fd);
        return -1;
    }

    // 成功加锁，操作文件...
    printf("成功获取文件锁，开始写入...\n");
    write(fd, "data", 4);

    // 解锁并关闭文件
    flock(fd, LOCK_UN);
    close(fd);
    return 0;
}
```

### 六、`fcntl` 函数详解

#### 1. 函数原型
```c
int fcntl(int fd, int cmd, ... /* 可变参数 */ );
```

- **返回值**：成功取决于 `cmd`，失败返回 `-1` 并设置 `errno`。
- **可变参数**：第三个不定量参数根据 `cmd` 不同，可能是整数 `int`，也可能是结构体指针 `struct flock *`。

---

#### 2. 功能说明
`fcntl`（file control）是 Linux C 编程中一个**功能极其丰富**的系统调用，堪称文件操作的“瑞士军刀”。它能够对已打开的文件描述符执行多种控制操作，包括复制描述符、获取/设置文件状态标志、管理记录锁（文件锁）、设置异步 I/O 通知等。

---

#### 3. 返回值
- **成功**：返回值取决于具体的 `cmd` 命令（见下文各命令说明）。
- **失败**：返回 `-1`，并设置全局 `errno` 以指示具体错误。

---

#### 4. 所需头文件

| 头文件                | 必要性       | 说明                                                         |
| --------------------- | ------------ | ------------------------------------------------------------ |
| `#include <fcntl.h>`  | **必须**     | 提供 `fcntl` 函数声明，以及所有 `cmd` 常量（`F_DUPFD`、`F_GETFL`、`F_SETFL`、`F_GETLK`、`F_SETLK`、`F_SETLKW` 等）和 `struct flock` 结构体定义。此头文件是所有文件控制操作的核心接口所在地。 |
| `#include <unistd.h>` | **隐含必需** | 虽然 `fcntl` 的声明在 `<fcntl.h>` 中，但实际使用时通常配合 `open`、`close`、`read`、`write` 等文件操作函数，这些函数声明于 `<unistd.h>`。此外，`STDIN_FILENO`、`STDOUT_FILENO` 等标准描述符常量也定义于此。 |

---

#### 5. 主要功能分类（按 `cmd`）

| 功能分类                         | cmd 常量                           | 作用简述                                         |
| :------------------------------- | :--------------------------------- | :----------------------------------------------- |
| **复制描述符**                   | `F_DUPFD` / `F_DUPFD_CLOEXEC`      | 复制文件描述符，返回新 fd                        |
| **获取/设置 close-on-exec 标志** | `F_GETFD` / `F_SETFD`              | 读写 `FD_CLOEXEC` 标志，控制 exec 时是否自动关闭 |
| **获取/设置文件状态标志**        | `F_GETFL` / `F_SETFL`              | 读写 `O_NONBLOCK`、`O_APPEND` 等标志             |
| **管理记录锁**                   | `F_GETLK` / `F_SETLK` / `F_SETLKW` | **精细粒度的文件锁（重点）**                     |
| **管理信号/通知**                | `F_GETOWN` / `F_SETOWN`            | 设置异步 I/O 的属主进程                          |
| **管道容量**                     | `F_GETPIPE_SZ` / `F_SETPIPE_SZ`    | 调整管道缓冲区大小（Linux 特有）                 |

---

#### 6. 各命令详解

##### 6.1 复制文件描述符：`F_DUPFD`

- **作用**：查找大于或等于参数 `arg` 的最小且仍未使用的文件描述符，并复制 `fd` 指向的文件对象。
- **返回值**：成功返回新复制的文件描述符。
- **特性**：新描述符与 `fd` 共享同一文件表项（`struct file`），但拥有自己独立的文件描述符标志，其中 `FD_CLOEXEC` 标志被清除。
- **参考**：相当于 `dup(int oldfd)` 。

##### 6.2 获取/设置 close-on-exec 标志：`F_GETFD` / `F_SETFD`

- **`F_GETFD`**：取得 close-on-exec 标志。若 `FD_CLOEXEC` 位为 0，代表在调用 `exec()` 族函数时文件**不会**自动关闭，子进程会继承这个文件描述符，与父进程同时操作同一个文件。
- **`F_SETFD`**：设置 close-on-exec 标志，由参数 `arg` 的 `FD_CLOEXEC` 位决定。
- **典型场景**：管道、文件描述符在子进程中的继承控制。

##### 6.3 获取/设置文件状态标志：`F_GETFL` / `F_SETFL`

- **`F_GETFL`**（FL = Flags）：取得文件描述符状态标志，即 `open()` 时的 `flags` 参数。
- **`F_SETFL`**：设置文件描述符状态标志。参数 `arg` 为新标志，但**只允许修改 `O_APPEND`、`O_NONBLOCK` 和 `O_ASYNC`**，其他位（如读写模式）不受影响。

```c
int flags = fcntl(fd, F_GETFL);          // 获取当前标志
flags |= O_NONBLOCK;                     // 添加非阻塞标志
fcntl(fd, F_SETFL, flags);              // 设置新标志
```

##### 6.4 记录锁操作：`F_GETLK` / `F_SETLK` / `F_SETLKW`

- **`F_GETLK`**（LK = Lock）：检测文件锁定的状态。
- **`F_SETLK`**：设置文件锁定的状态。若无法建立锁定，立即返回 `-1`，`errno` 为 `EACCES` 或 `EAGAIN`。
- **`F_SETLKW`**（W = Wait）：与 `F_SETLK` 作用相同，但无法建立锁定时会**一直阻塞等待**，直到锁可用。若在等待过程中被信号中断，则立即返回 `-1`，`errno` 为 `EINTR`。

---

#### 7. 记录锁核心结构体 `struct flock`

```c
struct flock {
    short l_type;     // F_RDLCK(读锁), F_WRLCK(写锁), F_UNLCK(解锁)
    short l_whence;   // SEEK_SET, SEEK_CUR, SEEK_END (与 l_start 配合)
    off_t l_start;    // 起始偏移
    off_t l_len;      // 锁定长度（0 表示锁定到文件末尾）
    pid_t l_pid;      // 持有锁的进程ID（F_GETLK 时返回）
};
```

#### 记录锁示例：锁定文件的前 100 个字节

```c
struct flock lock;
lock.l_type = F_WRLCK;        // 写锁（独占）
lock.l_whence = SEEK_SET;     // 从头开始
lock.l_start = 0;             // 起始偏移 0
lock.l_len = 100;             // 锁定 100 字节（0~99）
lock.l_pid = 0;               // 调用时置 0

// 阻塞式加锁（等待直到成功）
if (fcntl(fd, F_SETLKW, &lock) == -1) {
    perror("加锁失败");
    exit(1);
}

// 操作文件区间...
read(fd, buf, 100);

// 解锁
lock.l_type = F_UNLCK;
fcntl(fd, F_SETLK, &lock);
```

---

#### 8. `fcntl` 记录锁 vs `flock` 对比

| 特性             | `flock`               | `fcntl` 记录锁                    |
| ---------------- | --------------------- | --------------------------------- |
| **锁粒度**       | 整个文件              | **可锁定文件的任意字节区间**      |
| **锁类型**       | 共享/独占             | 共享（读锁）/独占（写锁）         |
| **锁与 fd 关系** | 与 fd 表项绑定        | **与进程 + inode 绑定**（更稳定） |
| **锁继承**       | fork 继承，close 释放 | fork **不继承**，exec 可选继承    |
| **NFS 支持**     | 有限                  | **更好**（需挂载选项）            |

---

#### 9. 关键特性与注意事项

1. **锁的粒度是“字节区间”**：可以锁定文件的任意一段，如只锁第 100~200 字节，其他区域不受影响。这对数据库、索引文件等并发读写场景至关重要。

2. **锁与进程、inode 绑定**：
   - 同一进程多次对同一区间加锁，**后一次会覆盖前一次**。
   - **`fork()` 不继承**记录锁（子进程需重新加锁），与 `flock` 不同。
   - 进程退出时，所有记录锁自动释放。

3. **锁转换（升级/降级）**：可直接对已持有的锁区间再次调用 `F_SETLK` 改变类型。若冲突，`F_SETLK` 返回错误，`F_SETLKW` 阻塞等待。

4. **建议性锁**：与 `flock` 一样，`fcntl` 锁也是**建议性**的，不守规矩的进程依然可以直接读写。

5. **`fcntl` 与 `flock` 锁不互通**：两套独立的锁机制，互相感知不到对方。

---

#### 10. `fcntl` vs `flock` 选型建议

| 场景                               | 推荐           | 原因                                  |
| ---------------------------------- | -------------- | ------------------------------------- |
| 只需锁整个文件，逻辑简单           | `flock`        | 调用简单，代码清晰                    |
| 需要锁定文件部分区域（如数据库页） | `fcntl` 记录锁 | 精细控制，性能更好                    |
| 需要跨 NFS 网络文件系统            | `fcntl`        | NFS 对 `fcntl` 支持更好（需挂载选项） |
| 需要子进程独立加锁                 | `fcntl`        | fork 不继承，符合预期                 |

---

#### 11. 高级特性（快速了解）

- **`F_GETPIPE_SZ` / `F_SETPIPE_SZ`**：调整管道缓冲区大小（Linux 2.6.35+）。
- **`F_GET_SEAL` / `F_ADD_SEALS`**：文件密封（sealing），用于 memfd 和共享内存，防止文件被修改。
- **`F_OFD_GETLK` 等**：Open File Description（OFD）锁，Linux 3.15+ 引入，锁与打开文件描述（而非进程）绑定，行为更接近 `flock` 但支持区间锁定。
